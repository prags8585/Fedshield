# FedShield — Architecture Diagram Brief

> Use this document as the source content for an AI diagram generator (e.g. Google Gemini).
> It describes one continuous, end-to-end flow — render it as a single flowchart, top to bottom,
> not a set of disconnected boxes. Three parallel lanes at the top converge into one shared
> layer, continue through a linear agent chain, fork twice near the end, and one branch loops
> back to the very top to close the loop.

## One-line description
Three bank branches each score transactions locally, but only a shared, anonymized graph can
prove that three separately-flagged deposits are actually the same laundering scheme.
Autonomous AI agents trace it, confirm it, generate a report, and feed the confirmed verdict
back in as a training label — closing the loop and making every branch's model smarter.

## Visual language / legend (carry this into the diagram)
- **Solid/moving brass (gold) line** — a live, fully autonomous step (code or an AI agent acting
  on its own, no human involved).
- **Solid/moving teal line** — a proven, cross-branch link inside the shared graph (a real money
  trail, not a guess).
- **Dashed grey/static line** — either (a) a lead that was investigated and cleared (dead end,
  did not converge), or (b) a step that is planned but not yet built.
- **Dashed-border box** — a "planned, not yet built" component (currently: Report Agent, Human
  Review).
- **Double-ringed circle stamp** — a rendered verdict ("CONFIRMED FRAUD").
- Color family: dark background; brass/gold for the "local branch → live autonomous" path; teal
  for the "shared graph / proven link" path; muted grey for cleared/planned/static links; red for
  the confirmed-fraud stamp.

## 1. Three branch lanes (top of diagram, side by side: loc1, loc2, loc3)

Each lane is identical, just a different branch label. Each lane is a vertical chain of 3 steps:

1. **DEPOSIT** — `CASH_DEPOSIT`, $8,000–$9,800, just under the $10,000 CTR reporting line.
   **Tool:** synthetic data generated by **Faker** (`simulator/customers.py`,
   `simulator/layering_scenario.py`), streamed onto the branch's own topic by a
   **Kafka producer** (`branch_node/producer.py`, `kafka-python`).
2. **MASK** — `SHA256(account + GLOBAL_SALT)` → an anonymous `token_id`, streamed via Kafka
   (`txns.loc1` / `txns.loc2` / `txns.loc3`).
   **Tool:** **Apache Kafka** for the transport; Python's built-in `hashlib` for the SHA-256
   masking (`branch_node/masking.py`), consumed by a **Kafka consumer**
   (`branch_node/consumer.py`) running inside its own **Docker** container per branch.
3. **SCORE** — a PyTorch logistic-regression scorer. Flags real layering hops well, but also
   flags roughly 30% of ordinary legitimate transfers (noise) — a single branch alone cannot
   tell a real hop from a look-alike.
   **Tool:** **PyTorch** (a single trained logistic-regression layer,
   `branch_node/model.py` / `train_model.py`), one model per branch, each running inside that
   branch's own **Docker** container.

Each lane's SCORE step feeds downward into the shared layer below (funnel: 3 lanes converge
toward the center).

## 2. Shared layer (one wide horizontal band, below the three lanes)

This is the only place any data crosses a branch boundary — and only an anonymized `token_id`
plus amount/time/channel ever cross it, never a name or account number.

- **REDIS** — the shared whiteboard. `fraud_events` is a pub/sub trigger (fires the instant a
  deposit is flagged — not a polling loop).
  **Tool:** **Redis** (pub/sub channel + key/value store), accessed via the `redis-py` client.
- **The shared graph (Neo4j)** — same `token_id` everywhere, so the same real account is the same
  node no matter which branch touched it. Inside this graph:
  **Tool:** **Neo4j** (graph database), written to by `branch_node/graph_writer.py` and queried
  via Cypher through `graph/queries.py`'s `check_convergence()`, `get_outgoing_txns()`,
  `get_incoming_txns()` (Neo4j's official Python `bolt` driver).
  - Each branch's flagged deposit becomes a **source node** (brass dot).
  - From each source, two possible paths:
    - A **dashed grey path to a "cleared" dead-end node** — a lead that never converges; cleared
      automatically, no human involved.
    - A **solid teal path to a real "layering hop" node** — time- and amount-verified against the
      previous transfer.
  - All three real hop paths converge on one **consolidation node** (`check_convergence()`
    confirms: 3 sources, 2+ branches, ~96% of value preserved).
  - The consolidation node has one outgoing solid teal edge to a **sink node** (`CASH_OUT` — the
    laundering exit / large withdrawal).

Two live/autonomous (brass) edges leave the shared layer and drop down into the agent chain:
- Redis's trigger → the first agent (Structuring).
- The graph's confirmed convergence result → the second agent (Money-Trail), queried live, never
  pre-computed.

## 3. Agent chain (one horizontal row, left to right)

A linear, autonomous chain — each step hands off to the next automatically:

1. **STRUCTURE** (Structuring Agent) — one quick AI gut-check on the score. Context only now, no
   longer a hard gate.
   **Tool:** **LangGraph** node calling a local **Ollama**-hosted LLM (`qwen2.5:7b`), via the raw
   `openai` Python SDK pointed at Ollama's OpenAI-compatible endpoint.
2. **TRACE** (Money-Trail Agent) — traces the money, live. `check_convergence()` runs in code,
   automatically; evidence is never AI-typed/hallucinated.
   **Tool:** **LangGraph** (tool-calling loop) + local **Ollama** LLM (`qwen2.5:7b`) for judgment
   and narration only; the actual trace is a deterministic **Neo4j** Cypher call, not an LLM
   output.
3. **VERDICT** (Verdict Agent) — renders judgment: GUILTY, 0.9+ confidence.
   **Tool:** one **LangGraph** node, one call to the local **Ollama** LLM (`qwen2.5:7b`), no
   tools.
4. **REPORT** (Report Agent, *planned* — dashed border) — sits beside Verdict in the same row.
   Generates an Excel report of the guilty fraud transactions.
   **Tool (planned):** one LLM call (**Ollama**, `qwen2.5:7b`) to draft the write-up, exported to
   a workbook with **openpyxl**.

From **VERDICT**, the flow forks three ways:
- Down to a **CONFIRMED FRAUD** stamp (double-ringed circle, red) — the rendered verdict, drawn
  on its own line/row below the agent chain (not crowded into the same row as Verdict/Report).
- Down and across (long line) to **LABEL** (see section 4) — a direct, live/autonomous line.
- (Implicitly) the Verdict step and Confirmed stamp both feed the Report Agent's context.

From **CONFIRMED FRAUD**, a dashed line goes to **REPORT** (confirming the report is generated
only once fraud is confirmed).

From **REPORT**, a dashed line goes down to **HUMAN REVIEW** (*planned*, dashed border) —
positioned directly below Report. A person reviews the Excel report and signs off. This step is
explicitly a dead end for control flow: it never gates or blocks anything below/above it — it's
the one manual step in an otherwise fully autonomous pipeline.
**Tool (planned):** a small CLI script (`review_report.py`, plain Python — `--approve`/`--reject`),
no framework.

## 4. Label + retrain loop (bottom row)

- **RETRAIN** (Flower / FedAvg) — positioned on the LEFT.
  **Tool:** **Flower (`flwr`)** federated-learning framework — one `fl_server/server.py` running
  `FedAvg`, plus one `branch_node/fl_client.py` per branch, each wrapping that branch's own
  **PyTorch** model.
- **LABEL** (Label Generator, code not an LLM call) — positioned on the RIGHT, receives the long
  live/autonomous line from VERDICT above. Writes a real training label: `(features, label=fraud,
  source=agent_verified)`.
  **Tool:** plain Python (`agents/label_generator.py`) writing directly to **Redis**
  (`labels:{branch}`) — deliberately not an LLM call.
- A solid brass arrow runs from **LABEL → RETRAIN** (right to left).
- **RETRAIN** does FedAvg across all three branches (loc1/loc2/loc3), blending the new label into
  the next training round.
- From **RETRAIN**, one long, sweeping solid brass line loops all the way back up and around to
  the top of the diagram, arriving back at the **branch lane headers (loc1/loc2/loc3)** — visually
  closing the loop. Label this arc: "closes the loop — verdict → label → retrain → smarter model,
  next round."

## Tech-stack summary (one tool per component — good for icon/badge labels)

| Component | Tool / Library |
|---|---|
| Deposit (synthetic data) | Faker |
| Transport (branch → shared layer) | Apache Kafka (`kafka-python`) |
| Branch isolation | Docker (one container per branch) |
| Mask (`token_id`) | Python `hashlib` (SHA-256) |
| Score | PyTorch (logistic regression) |
| Shared whiteboard / trigger | Redis (pub/sub) |
| Shared money-trail graph | Neo4j (Cypher via the `bolt` driver) |
| Structuring / Trace / Verdict agents | LangGraph + local Ollama LLM (`qwen2.5:7b`) |
| Report Agent (planned) | Ollama LLM + openpyxl (Excel export) |
| Human Review (planned) | Plain Python CLI script |
| Label Generator | Plain Python (no LLM), writes to Redis |
| Retrain | Flower (`flwr`) FedAvg, wrapping each branch's PyTorch model |

## Notes for whoever builds this in Gemini
- Keep it to ONE flowing diagram, not separate disconnected boxes — every node should have at
  least one visible connecting line in and (except terminal/dead-end nodes) one out.
- The three branch lanes should look identical/symmetric (same 3 steps, same styling), just
  labeled loc1/loc2/loc3.
- The "cleared" dead-end nodes and the "planned" Report/Human Review nodes should look visually
  de-emphasized (muted color, dashed border) compared to the live/autonomous path.
- The loop-back arc from Retrain to the top branch lanes is the single most important visual
  element for conveying "this is a closed, self-improving loop" — make it a clear, sweeping,
  unmistakable arc, not a small arrow.
